# Go 后端项目学习路线

适用起点：已有 SQL 基础和 Go 基本语法，已经读过[项目架构与业务调用链学习指南](项目架构与业务调用链学习指南.md)。最终目标有两个：**能独立解释、调试本项目的全部业务模块**；**能在空项目中独立搭建同类后端的可用版本**。路线按“主干入门 → 全模块理解 → 独立重建 → 综合验收”推进，现有项目可作为对照。

第 1～6 步用于理解主干，之后的全模块阶段补齐覆盖，再通过从 0 到 1 的独立实现检验能力。**读完、跑通和真正掌握是三个不同层次；每阶段以输出和验收题过关，不按天数划分进度。**

这份大纲是学习的**导航和验收清单**，不是唯一教材。每一步都要配合实际代码、HTTP 请求及 MySQL/Redis/RabbitMQ 中的数据观察；遇到陌生概念，再查该技术的官方文档。按下面的循环学习，不必先把所有技术理论读完：

1. 看本阶段目标，先画出自己预测的请求、数据和消息流向。
2. 沿路由 → Handler → Service → Repository/中间件/Worker 阅读代码，标出关键字段是谁写、谁读。
3. 亲自发请求或停启依赖，对照响应、日志和存储结果修正预测；至少试一次有代表性的失败或边界情况。
4. 合上代码，用自己的话讲清业务作用、调用顺序、数据变化和失败时会怎样；讲不清的地方再回代码验证。

Go 基础语法之外，按需补以下前置知识即可：注册阶段学 HTTP 请求/状态码、JSON 绑定与校验、错误返回；数据库阶段学 `context.Context`、事务和唯一约束；Redis 阶段学过期时间与常用数据结构；Worker 阶段学 goroutine、Go channel 与 RabbitMQ channel 的区别、消息确认与重复消费。先理解这些概念如何在本项目中出现，再逐渐扩展深度。

## 1. 跑通一条同步写库链：注册

**目标：**看懂一次 HTTP 请求如何经过 Handler、Service、Repository，最终写入 MySQL。

```text
POST /account/register
  → AccountHandler.CreateAccount
  → AccountService.CreateAccount
  → AccountRepository.CreateAccount
  → MySQL accounts 表
```

**动手验证：**发送注册请求，记录请求 JSON 和响应；在 MySQL 查新账号；把 `CreateAccount` 对应到你熟悉的 `INSERT`。再看密码在哪一层被哈希。

**完成标准：**能指出每一层接收了什么、返回了什么，以及哪一行真正写库。

代码入口：[路由](../backend/internal/http/router.go)、[Handler](../backend/internal/account/handler.go)、[Service](../backend/internal/account/service.go)、[Repository](../backend/internal/account/repo.go)。

## 2. 理解登录与鉴权

**目标：**分清 JWT 的生成、HTTP 鉴权和项目保存的当前有效 Token。

**动手验证：**调用 `/account/login`；带返回的 Token 访问 `/social/getCounts`；再调用 `/account/logout`，观察同一个 Token 后续请求的结果。沿 [账号业务层](../backend/internal/account/service.go) 和 [JWT 中间件](../backend/internal/middleware/jwt/jwt.go) 跟踪。

**完成标准：**能解释 Token 从哪里来、放在请求的什么位置、为何登出后旧 Token 不再通过普通 JWT 鉴权。

## 3. 理解事务和表关系：发布视频

**目标：**把 Go 结构体对应到 MySQL 表，理解多项写入为何放在一个事务里。

**动手验证：**上传视频和封面，使用返回的 URL 发布一条标题带 `#话题` 的作品；查询 `videos`、`tags`、`video_tags`，画出 ID 之间的关系。阅读 [视频实体](../backend/internal/video/video_entity.go)、[标签实体](../backend/internal/video/tag_entity.go)和 [VideoService.Publish](../backend/internal/video/video_service.go)。

发布时还会写一条 `OutboxMsg`：它是 MySQL 中等待发送的任务记录，后台投递成功后会删除，所以正常运行时不一定能查到这条记录。先理解 `Video`、`Tag`、`VideoTag`、`OutboxMsg` 各自存什么，再学习后续的 RabbitMQ 时间线。

**完成标准：**能说出“上传文件”和“发布视频”的区别，以及事务里任一写入失败时会发生什么。

## 4. 理解 Redis：先学详情缓存，再学时间线

**目标：**分清缓存对象、排序集合和 MySQL 原始数据。

**动手验证：**用同一个 ID 连续请求两次 `/video/getDetail`，沿 [VideoService.GetDetail](../backend/internal/video/video_service.go) 看“缓存命中”和“未命中后回填”两条路径。然后查看 `/feed/listLatest`：Redis `feed:global_timeline` 存视频 ID，分数是发布时间；[FeedService](../backend/internal/feed/service.go) 再根据 ID 取视频数据。

**完成标准：**能回答 Redis 在这两条路径各存什么、什么时候还要查 MySQL、Redis 不可用时走哪条路径。

## 5. 理解 RabbitMQ 和独立 Worker：点赞

**目标：**分清发布消息、队列路由、消费消息和处理完成。

```text
POST /like/like → LikeService.Like → LikeMQ 发布事件
  → RabbitMQ like.events 队列
  → LikeWorker.Consume → 更新 MySQL → Ack
```

**动手验证：**先在 API 和 Worker 都运行时点赞，确认 MySQL 的点赞记录与计数变化。然后停掉独立 Worker，用另一组尚未点赞的用户和视频再发一次点赞请求；观察 RabbitMQ 队列中的待处理消息，重启 Worker 后观察数据变化。只做一次请求，避免把重复点赞与异步时序混在一起。

**完成标准：**能区分“HTTP 已响应”“消息已发布”“Worker 已写库”三个时间点，并能指出 [发布位置](../backend/internal/middleware/rabbitmq/likeMQ.go)、[消费位置](../backend/internal/worker/likeworker.go)、[Worker 入口](../backend/cmd/worker/main.go)。

## 6. 串起完整视频流：Outbox 到 Feed

**目标：**理解发布视频后，最新视频流如何更新。

```text
MySQL 视频 + OutboxMsg
  → API 内 Outbox 轮询器
  → RabbitMQ 时间线队列
  → API 内时间线消费者
  → Redis feed:global_timeline
  → /feed/listLatest
```

**动手验证：**发布一条视频，沿 [Outbox 与时间线消费代码](../backend/internal/worker/outboxworker.go) 和 [TimelineMQ](../backend/internal/middleware/rabbitmq/timelineMQ.go) 记录视频 ID 在每一步如何表示，最后请求 `/feed/listLatest` 找到该视频。

**完成标准：**能区分 `OutboxMsg`（MySQL 待办记录）、`TimelineEvent`（RabbitMQ 消息）、Redis 排序集合成员（视频 ID）。

## 全模块阶段：把主干扩展为完整项目

前六步只覆盖典型链路，不能代表已理解所有功能。下面逐组查阅[完整接口清单](项目架构与业务调用链学习指南.md)：**每条路径都要能说出业务作用、输入、输出、调用去向和数据来源；每组至少亲自走通一次写操作和一次读操作**，再完成对应验收。相似路径可以对比学习，不要求逐文件背诵实现。

| 阶段 | 覆盖范围 | 必做实验 | 过关标准 |
| --- | --- | --- | --- |
| 7. 账号与身份 | `/account` 的 11 条路径；普通 JWT、软鉴权、刷新与撤销 Token、资料与主页统计 | 注册、登录、刷新、改名、改密、登出各做一次；对照 MySQL 和 Redis 的 Token 状态 | 能解释每种操作后旧 Token 是否还能用，以及个人主页的统计来自哪些表 |
| 8. 视频与文件 | `/video` 的 9 条路径；普通上传、分片续传、封面、发布、话题、详情缓存 | 上传和发布一条带 `#话题` 的视频；暂停分片后用状态接口续传；查 `videos`、`tags`、`video_tags` | 能画出上传会话、文件、视频记录、标签关系和 Outbox 记录；说清 Redis 不可用时分片上传会怎样 |
| 9. 社交与互动 | `/like` 4 条、`/comment` 3 条、`/social` 5 条、`/message` 2 条 | 用两个账号完成点赞/取消、评论/删除、关注/取关、私信；核对记录和计数 | 能区分哪些操作同步写 MySQL、哪些先发 MQ；能解释“接口已返回但查询仍是旧值”的原因 |
| 10. 五种 Feed | `/feed` 的 5 条路径；时间线、累计点赞榜、近期热榜、关注流、话题流和分页游标 | 给不同时间、点赞数、话题的视频造数据；逐条查询并翻到下一页 | 不看代码能预测每条路径的筛选与排序依据、用户身份是否必需、Redis 与 MySQL 各做了什么 |
| 11. 通知与后台链 | `/notification` 的 4 条路径；独立 Worker、API 内通知消费者、SSEHub、Outbox 和时间线消费者 | 保持 SSE 连接，触发点赞或关注，核对通知表与实时推送；跟踪一次视频发布到最新流 | 能区分三个执行位置：HTTP Handler、独立 Worker 进程、API 内后台 goroutine；能解释 `Ack`、待发送记录和通知持久化 |
| 12. 运行与故障 | 配置、依赖启动、限流、测试、Compose、健康检查 | 分别停独立 Worker、Redis、RabbitMQ，先预测再观察一条相关业务链；运行现有测试与构建 | 能说清哪些路径降级、哪些路径不可用，并依据日志或数据指出处理停在哪一步 |

每个阶段留下三份学习产物：**一张调用图、一份字段与实际存储的对照表、一段亲自验证的记录**。这三份产物能暴露“会复述名词，却不知道数据何时改变”的盲点。遇到行为与预期不同时，先检查代码和实际结果，再修正自己的图。

故障实验在本地练习环境进行，使用可以重新创建的测试数据。重点是观察当前代码的真实行为，例如 Redis 对普通缓存可选，但分片上传必须有 Redis；消息进入队列也不等于 Worker 已经写库。

## 从 0 到 1 重建后端

这部分以一个新的练习项目为对象，目标是**亲手做出最小可用的短视频后端，再逐步加上缓存、消息和工程能力**。每个阶段都以前一阶段能运行作为起点。前几个阶段只需要 MySQL；Redis 和 RabbitMQ 在真正需要它们时再接入。

| 阶段 | 亲手实现什么 | 可运行的验收结果 | 对照本项目 |
| --- | --- | --- | --- |
| 0. 起步 | 建 Go module、`main`、配置读取、Gin `/healthz`；准备本地 MySQL | `go run` 后请求 `/healthz` 得到成功响应 | `backend/cmd/main.go`、`internal/config`、`internal/http` |
| 1. 第一张表与第一个接口 | 设计 `accounts` 表/实体；连 MySQL；写 Repository、Service、Handler 和 `/account/register` | 注册后能用 SQL 查到账号，密码不是明文 | `internal/db`、`internal/account` |
| 2. 登录和受保护接口 | 校验密码、签发 JWT；加鉴权中间件；做一个只允许登录用户访问的接口 | 无 Token 被拒绝，正确 Token 能访问；登出后旧 Token 失效 | `internal/auth`、`internal/middleware/jwt` |
| 3. 视频发布与基础 Feed | 设计 `videos` 表；先实现上传/保存文件、发布视频、按发布时间从 MySQL 分页查询 | 能上传、发布，并在 `/feed/listLatest` 找到作品 | `internal/video`、`internal/feed` |
| 4. 补齐最小业务闭环 | 做点赞/取消点赞、评论、关注和关注流；练习唯一约束、事务和关联查询 | 两个用户能发布、浏览、互动；计数和关系能用 SQL 核对 | `internal/video`、`internal/social`、`internal/feed` |
| 5. 加 Redis | 给视频详情加缓存；给最新流建时间线 ZSET；再加热榜或限流 | 能分别观察缓存命中、过期、回源和排序结果；Redis 不可用时明确知道哪些接口降级 | `internal/middleware/redis`、`internal/video`、`internal/feed` |
| 6. 加 RabbitMQ 和 Worker | 把一个互动操作改成发布消息并由独立 Worker 消费；实现确认、失败重试与重复消息处理 | 停 Worker 时消息待处理，重启后数据完成更新；重复事件不会重复增加点赞 | `internal/middleware/rabbitmq`、`cmd/worker`、`internal/worker` |
| 7. 加 Outbox | 发布视频时同一事务写视频与待发送事件；轮询器发 MQ；消费者更新 Redis 时间线 | 视频写入与待发送记录一起提交；重启处理后视频仍能进入最新流 | `VideoService.Publish`、`OutboxMsg`、`outboxworker.go` |
| 8. 扩展体验 | 按需加入话题、私信、通知/SSE、分片上传；接一个最小前端页面或继续用 HTTP 客户端调试 | 每加入一项功能，都能从请求追踪到存储或推送结果 | `internal/message`、`internal/worker/ssehub.go`、`frontend` |
| 9. 收尾验证 | 给关键业务规则和失败路径加测试；用 Compose 启动 API、Worker 和依赖；检查配置、健康接口与日志 | 从空环境按文档启动，跑通注册→发布→浏览→互动；测试与构建通过 | `docker-compose.yml`、`.github/workflows/ci.yml` |

**重建表中的第 4 阶段完成，就是第一个可用版本。** 此时有账号、视频、基础 Feed 和互动，可以先用 MySQL 完成业务。之后再加性能和异步处理。重建的目标是证明你能独立作出结构、数据和错误处理选择；不是按原仓库文件顺序抄一遍。若目标只限 Go 后端，前端可先用 Postman 集合 `test/postman.json` 或其他 HTTP 客户端替代。

重建时建议保留这三个约束：

1. **每阶段都能运行。** 接口、数据库结果、失败响应都要能观察；不要一次写完所有模块才启动。
2. **先定义数据，再写调用链。** 对每个功能先写出请求字段、涉及的表和唯一约束，再实现 Handler → Service → Repository。
3. **先做一条完整路径，再加复杂能力。** 例如先让点赞同步写库并核对结果，再引入 MQ；引入异步后重新验证“接口成功返回”和“数据库已更新”的时间差。这是练习顺序，不代表现有项目的点赞实现是同步的。

可选的官方资料：[Go 测试入门](https://go.dev/doc/tutorial/add-a-test)、[GORM 迁移](https://gorm.io/docs/migration.html)、[RabbitMQ Go 工作队列教程](https://www.rabbitmq.com/tutorials/tutorial-two-go/)、[Docker Compose 应用模型](https://docs.docker.com/compose/intro/compose-application-model/)。遇到对应阶段再查，随后回到自己的实现验证。

## 最终验收：怎样判断自己“吃透了”

计划本身不能保证掌握；需要用不看指南、独立完成的任务来验证。以下三项全部通过，才算达到本路线的目标：

1. **解释现有项目。** 对照路由逐条说出所有业务路径的作用、输入输出和数据来源；从账号、视频、点赞、评论、关注、Feed、私信、通知中各随机选一条路径，独立画出从请求到数据/消息/响应的链，并说明关键字段、正常路径和失败路径。还要能解释启动时 API 与独立 Worker 各注册了哪些后台任务，以及停掉其中一个进程会影响哪些链路。
2. **独立定位问题。** 在本地制造一个可恢复的条件变化，例如 Worker 暂停或 Redis 不可用；先预测哪个接口和哪份数据受影响，再查代码、日志、MySQL/Redis/MQ 验证。不借助现成答案说明原因与恢复方式。
3. **独立构建可用版本。** 在空项目中完成注册登录、视频发布、基础 Feed、点赞/评论/关注；再为详情加缓存，为一项互动加消息和 Worker，并提供至少一项有实际断言的测试。能从本地启动并走通“注册 → 发布 → 浏览 → 互动”。

通过这三项可以说明：你不仅认识本项目的模块，也具备从 0 到 1 搭建**同类后端基础版本**的能力。完整复刻本仓库的每项体验或独立运营生产系统，是更大的目标；需要继续完成重建表中的第 8 阶段扩展功能和工程实践。

## 每次实验的记录方式

把笔记放在 `doc/`，一条业务链记录四项即可：

```text
业务与接口：
请求字段和返回值：
调用顺序：
MySQL / Redis / RabbitMQ 中观察到的变化：
```

遇到不懂的字段，先在 `entity.go` 中找定义，再查是谁给它赋值、谁读取它。例如 `OutboxMsg.VideoID` 在发布视频时赋值，在轮询器发送时间线事件时读取。
